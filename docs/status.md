# 구현 기록

## 기본 앱 실제 ARS → B/C/D 연결 (2026-10-27)

- 사용자 승인: 기본 앱의 기존 ARS Agent 전화 버튼부터 실제 API·B/C/D·음성 기능 연결. 디자인·A 일반 전화 데모·고정 미리보기·기존 debug 서버 테스트 유지. 백엔드 수정·구현자의 실제 발신·추가 런처·푸시·main 병합 없음.
- 기본 앱 이름은 ARS Agent, 기본 모드는 실제 ARS. 기존 상단 메뉴에서 이전 UI 데모를 선택할 수 있다. `MainCallViewModel`/`LiveCallOwner`가 단일 실제 세션을 소유하며 `AppViewModel`은 데모용으로 유지한다. 공통 controller/voice를 debug에서 main으로 이동해 재사용하고 필요한 RECORD_AUDIO/MODIFY_AUDIO_SETTINGS·STT/TTS queries만 추가한다. A/갤러리는 네트워크·마이크를 열지 않는다.
- 목적 입력은 확인창만 준비한다. 번호·목적·실제 발신 경고·일회성 API 키 입력 후 사용자가 실제 발신을 눌러야 한 번 생성한다. 키는 비저장·비복원, 생성/전송 불확실 시 자동 재시도 없음. 실통화 준비/세션에만 FLAG_SECURE 적용.
- B는 서버 snapshot/경로/자막/결과, C는 서버 후보 select·일반 answer·secure_input·수동 key, D는 실제 상담원 대기/연결 상태. 음성/버튼 공통 요청별 중복 게이트와 권한·기한·최신 요청 검증 유지. 종료는 서버 확인을 기다리고 최종 서버 시간을 우선한다.
- B01 실제 마이크는 음성 서비스 안내/권한 동의 후 한 번 듣고 목적만 채운다. 통화 중 Agent 진행·질문 TTS 후 일반 답변 STT, ARS 수신 재생, 실제 휴대전화/스피커 라우팅을 연결한다. 중요 선택·개인정보는 음성 입력 제외. 백그라운드에서는 음성 중단/오디오 복원, 상담원 사용자 음성은 지원하지 않는다.
- TDD: 미구현 소유자·권한 대기·오디오 라우팅 테스트 RED 후 구현. 가상 gateway/음성 장치 및 로컬 REST/WS로 단일 확인 발신, 상태/버튼 전송, 음성 경쟁·종료를 확인한다. 에뮬레이터 화면은 실제 발신 직전까지만 확인하며 배포 서버 인증/발신/음질·인식 정확도는 사용자 테스트 항목이다.
- UI 검증 중 두 테스트 fixture 문제를 기록: 이미 키보드 높이를 뺀 짧은 창에서 IME inset 이중 차감, 직전 key 응답 완료 전 테스트가 비활성 답변 필드에 입력하는 경합. 제품 레이아웃은 바꾸지 않고 fixture의 inset 소비/실제 송신 가능 대기를 보정했다. 최종 전체 검증 결과는 아래 후속 기록에 남긴다.
- 최종 구현 검증: 단위 152개·Android UI 93개 통과. lint 오류 0/기존 경고 11개, debug/release APK 성공. 실제 발신 없이 native 음성 동의 취소·오디오 모드 복원 및 합성 A/B/C 레이아웃 확인. 배포 키·발신·실제 STT/TTS/ARS 종단간 성공을 주장하지 않는다.

## 최신 변경 푸시 준비·연결 정리 버그 수정 (2026-10-27)

- 사용자 요청: 현재까지 로컬 변경을 `feat/compose-mvp`에 커밋·푸시. `main` 병합과 백엔드 변경은 하지 않는다.
- 서버의 health 응답을 정상 수신한 뒤 UI 스레드에서 TLS 연결을 정리하면서 `NetworkOnMainThreadException`이 발생하고 네트워크 오류로 잘못 표시되던 문제를 재현했다. API 클라이언트는 즉시 닫힘 상태로 전환하고, 소켓 정리·요청 취소·executor 종료는 소유한 백그라운드 executor에서 실행하도록 수정했다.
- 실제 pooled socket을 사용하는 재발 방지 테스트에서 수정 전 호출 스레드 정리 실패, 수정 후 별도 스레드 정리를 확인했다. 단위 133개 통과, lint 오류 0/기존 경고 11개, debug/release APK 빌드 성공. Android UI 78개는 최초 실행에서 `secureInputWaitsForExplicitSendAndDoesNotAppendTerminator` 한 건 실패했으나 해당 클래스 9개 및 전체 78개 재실행은 모두 통과했다. 이 UI 코드는 변경하지 않았다.
- 에뮬레이터에서 같은 Android 스레드 제한의 제어 코드 진단과 실제 연결 확인 버튼 연속 3회 모두 오류 없이 health 응답을 확인했다. 키 사용·실제 발신·백엔드 수정은 하지 않았다.
- 기본 앱의 실제 ARS 중심 연결은 아직 미구현이다. `2026-10-27-main-live-call-design.md`는 구체 흐름 승인 전 초안이며, 이 푸시를 기본 앱 B/C/D 실제 연결 완료로 해석하지 않는다. 기본 데모·갤러리와 별도 서버 테스트를 구분하도록 README를 갱신했다.

## 서버 테스트 Agent 음성 대화·ARS 듣기 (2026-10-27)

- 사용자 승인: Agent 질문/핵심 진행 안내 TTS, 사용자 목적/일반 재질문 답변 STT, ARS 수신 재생을 debug 서버 테스트에 추가. 상담원 통화 제외. 기존 서버 테스트 화면·진입점·debug 권한의 최소 연결 수정은 추가 승인받음.
- 별도 debug 음성 모듈을 추가. 기존 컨트롤러/게이트웨이/API·main/데모/미리보기·백엔드는 변경하지 않음. 장식 게이트웨이는 기존 create 결과만 관찰하고 새 발신 경로를 만들지 않음. 목적 인식만으로 발신하지 않고 기존 실제 발신 확인 유지.
- 음성 대화는 명시적으로 켠 뒤 사용. 시스템 STT 외부 처리 가능성 안내와 마이크 권한 요청. 질문 TTS 후 단발 STT를 시작하고 유효한 현재 요청에 answer를 한 번 전달. 기한/질문/세션 교체와 백그라운드·중복 콜백 차단. 중요 선택/개인정보는 기존 버튼/키패드 유지.
- ARS는 동일 origin·경로로 인증된 WS에서 μ-law 수신 재생만 제공. 마이크 데이터 송신·redirect·자동 재발신 없음. TTS/STT 시작 전에 ARS 재생을 동기적으로 억제. 상담원 연결/종료/백그라운드에서 정리하며 음성 오류로 기존 통화 상태를 바꾸지 않음.
- 실제 키·배포 서버 호출·실제 마이크 녹음·발신·백엔드 변경·푸시/병합은 하지 않음. 실제 한국어 엔진과 배포 오디오 동작은 사용자의 실기기 검증이 필요.
- 최종 검증: JVM 132개·Android UI 78개(총 210개) 통과, 린트 오류 0/기존 경고 11개, debug/release APK 성공 (`/private/tmp/ars-voice-completion.log`, `.superpowers/sdd/2026-10-27-server-voice/task-2-tests.log`). main 전체 파일 해시 작업 전과 일치, release APK에 RECORD_AUDIO 없음.
- 독립 읽기 전용 리뷰 후 재생기 생성/쓰기/소거/상태 갱신을 세대별로 직렬화하고, 음성 답변을 화면 캐시가 아닌 최신 컨트롤러 요청 전체와 재검사하도록 수정. TTS 초기화 중 안내 교체에도 타임아웃 유지. 각각 실패하는 회귀 테스트 후 구현하고 전체 검증을 재실행했으며, 추가 리뷰 요청·실제 발신은 하지 않음.

## 서버 테스트 실통화 확인 (2026-10-27)

- 사용자 승인: 기존 debug 서버 테스트에서 실통화 준비·확인·발신 요청을 허용. 실제 발신은 사용자가 직접 수행하며 구현 검증은 가상 데이터와 로컬 MockWebServer만 사용.
- health의 sim은 기존 모의 시작, clawops는 ‘실통화 준비 → 번호·목적·실제 발신 경고 확인 → 실제 발신’ 순서. 실통화 번호는 빈칸에서 입력하며 앱이 서버 모드를 변경하지 않음. 알 수 없는 모드는 차단.
- 확인과 키는 저장/복원하지 않음. 확인을 먼저 소비한 뒤 명령을 전달하고 키 입력칸을 지움. 모드·대상·목적·활성 세션 변경 시 오래된 확인을 사용하지 않음. 생성 직전 health 재검사와 기존 중복·응답 유실 차단 유지.
- 기존 A 데모·화면 미리보기·B/C 서버 렌더러는 변경하지 않음. 새 아이콘·백엔드 설정 변경·실제 배포 요청·키 사용·푸시/병합 없음. 앱 음성 재생·마이크 전달은 아직 미구현이라고 안내.
- health 조회와 세션 생성은 원자적이지 않으므로 테스트 도중 서버 모드를 변경하지 않아야 함. 실제 인증·발신·오디오 검증은 별도 사용자 테스트가 필요.
- 독립 읽기 전용 리뷰에서 Critical/Important 없음. 추후 테스트 보완: 모의 전송 테스트의 생성 JSON 전체 동등성 비교(현재 번호 검사, 기존 직렬화 코드는 유지).
- 최종 검증: JVM 109개·Android UI 73개(총 182개) 통과. `lintDebug` 오류 0/기존 경고 11개, debug/release APK 빌드 성공 (`/private/tmp/ars-real-confirm-final.log`). 합성 UI 확인창 캡처로 대상 번호·경고·취소/발신 버튼 배치 확인. 배포 서버는 호출하지 않음.

## C 개인정보 입력·입력 완료 통일 (2026-10-27)

- 사용자 승인: 서버의 개인정보 안내 표시와 secure_input 전용 전송값을 준비하고, 모든 개인정보 입력에 ‘입력 완료’ 버튼 추가. 기존 디자인·데모·미리보기는 유지하되 데모 6자리 자동 제출을 제거. 일반 통화 수동 키패드는 변경하지 않음.
- 기존 원형 키패드는 카드 밖에 유지하고 완료 버튼을 종료 위에 고정. 데모의 6자리 예시는 명시적 완료로만 진행하며 갤러리는 버튼이 보여도 기존처럼 정지 상태 유지. debug 서버 진단 화면의 제출 버튼명도 통일.
- `SecureInputDraft`는 1~20자 API 제한과 서버 기한/종류/ID를 검사하고, 명시적 완료 시에만 `SessionAction.SecureInput`을 생성. 서버 지정 종료 기호를 중복 추가하지 않음. 서버 안내에서 기대 길이를 임의 추측하지 않음.
- `BServerCallScreen`에 선택적 `SecureInputInput` 추가. 세션/통신은 소유하지 않으며 기존 앱 진입점에는 연결하지 않음. CharArray 버퍼는 제출 전후, 만료·요청 교체·종료·연결 불가·백그라운드·해제 시 비우고 raw digits는 saved state/로그/파일에 넣지 않음. immutable String·네트워크 버퍼의 완전 삭제까지 보장하는 것은 아님.
- 중복 제출 기록을 통화 화면 최상위에 유지. 화면 크기 변경/요청 임시 제거로 같은 요청을 다시 보내지 않으며 명확한 미접수 오류에서만 소유자의 retryVersion 갱신 후 재입력 허용. 실서버 호출·발신·인증키 사용/저장·추가 아이콘·Figma 수정·푸시/병합 없음.
- 테스트 우선: 미구현 모델과 완료 버튼 부재 실패 재현 후 구현. 단위 101개·Android UI 66개(총 167개) 통과, 린트 오류 0/기존 경고 11개, debug/release APK 빌드 성공 (`/private/tmp/ars-secure-final-layout.log`). 로컬 MockWebServer에서 정확한 secure_input JSON·종료 기호 미추가·명시적 완료 전 무호출 확인. 독립 읽기 전용 리뷰에서 추가 결함 없음.
- 캡처 검증에서 추가 완료 버튼 때문에 키패드 아랫줄이 화면 밖으로 밀리는 점 발견. 초기 0번 키 가시성 실패를 재현한 뒤 중복 도움말을 줄이고 카운터를 입력 줄에 합침. 개인정보 입력의 세로 키 간격만 12dp로 줄였고 원형 키 72dp 크기·일반 키패드 24dp 간격·종료 위치는 유지. 수정 후 가시성/하단 겹침 테스트와 전체 회귀 재통과. 짧은 창과 긴 안내는 스크롤 유지.

## C 후보 선택 데이터 연결 준비 (2026-10-27)

- 사용자 승인 범위: 서버가 보내는 후보 표시와 선택값 전달 준비만 추가. 기존 디자인·데모·미리보기·진입점 유지, 실제 배포 서버 호출과 추가 아이콘 없음.
- `CandidateChoice`가 clarification의 질문·후보와 기한을 사용하고 `SessionAction.Select(requestId, key)`를 생성. 서버 후보 순서/라벨/번호 유지, `*`·`#`도 업무 선택지로 처리. critical_action은 버튼만 제공.
- 기존 B 통화 틀에 선택적 `CandidateChoiceInput`을 추가. 송신 가능/awaiting_user일 때만 활성화하며 빈 후보·중복 키·잘못된 기한·만료는 차단. 선택 후 서버 응답을 기다리며 로컬 진행/자동 재전송 없음. 명확한 미접수 오류에 한한 소유자의 retryVersion 변경만 재시도를 허용.
